Yes. Given your current Neo4j model, I’d design the API around exploration of the knowledge graph, rather than exposing your ingestion methods directly.

Your graph is roughly:

Document
   │
   └── CONTAINS → Chunk
                     │
                     └── SUPPORTS → Claim
                                      ├── SUBJECT → Entity
                                      └── OBJECT → Entity

Entity ── RELATES ──> Entity
              │
              └── type → RelationshipType

So the UI/API can naturally have three levels: entity → relationships → evidence/context.

1. Entity list / browse
Useful for your main "Entity Store" page.

GET /entities
Supports pagination, filtering, and search.

GET /entities?search=apple&type=Organization&page=1&page_size=25

Response:

{
  "items": [
    {
      "id": "ent_123",
      "name": "Apple Inc.",
      "normalize_name": "apple inc",
      "canonical_type": "Organization",
      "alias": ["Apple"],
      "description": "Technology company",
      "relationship_count": 42,
      "claim_count": 18
    }
  ],
  "page": 1,
  "page_size": 25,
  "total": 1
}

For this endpoint I'd add a Cypher query specifically for browsing rather than using search_entity_candidates(), since your current search method is primarily a candidate retrieval API.

2. Entity detail
This would probably be the most important endpoint.

GET /entities/{entity_id}
Return the entity plus summary information:

{
  "id": "ent_123",
  "name": "Apple Inc.",
  "normalize_name": "apple inc",
  "canonical_type": "Organization",
  "alias": ["Apple"],
  "description": "Technology company",
  "embedding_available": true,
  "stats": {
    "relationships": 42,
    "claims": 18,
    "documents": 7
  }
}

This powers an entity detail page.

3. Entity relationships
GET /entities/{entity_id}/relationships
This gives you the graph around an entity.

GET /entities/ent_123/relationships?direction=both&limit=50

Response:

{
  "items": [
    {
      "relationship_id": "rel_001",
      "type": "ACQUIRED",
      "description": "Apple acquired Beats",
      "direction": "outgoing",
      "source": {
        "id": "ent_123",
        "name": "Apple Inc.",
        "type": "Organization"
      },
      "target": {
        "id": "ent_456",
        "name": "Beats Electronics",
        "type": "Organization"
      }
    }
  ]
}

I'd support:

direction=outgoing
direction=incoming
direction=both

This is particularly useful for a graph visualization.

4. Entity neighborhood / graph endpoint
For a graph UI, I'd actually make a dedicated endpoint rather than forcing the frontend to assemble the graph.

GET /entities/{entity_id}/graph
Example:

GET /entities/ent_123/graph?depth=2&limit=100

Response:

{
  "nodes": [
    {
      "id": "ent_123",
      "label": "Apple Inc.",
      "type": "Organization"
    },
    {
      "id": "ent_456",
      "label": "Beats Electronics",
      "type": "Organization"
    }
  ],
  "edges": [
    {
      "id": "rel_001",
      "source": "ent_123",
      "target": "ent_456",
      "type": "ACQUIRED"
    }
  ]
}

This maps almost directly onto libraries such as React Flow, Cytoscape, D3, etc.

I'd make this endpoint optimized specifically for visualization.

GET /claims/{claim_id}

  "predicate": "acquired",
  "confidence": 0.96,
  "subject": {
    "id": "ent_123",
    "name": "Apple Inc."
  },

The 5 endpoints I'd build first
Don't build everything initially. For an entity/relationship store UI, I'd start with:

GET /entities — browse/search entities
GET /entities/{id} — entity details
GET /entities/{id}/graph — visualize neighborhood
GET /entities/{id}/context — show evidence
GET /graph/stats — dashboard statistics

One thing I'd change in your current driver
There are a couple of issues worth fixing before putting an API on top.

For example, this:

result = self.driver.execute_query(...)
if not result:
    return None

return EntityNode.model_validate(result)

isn't validating the returned Neo4j result correctly. execute_query() returns an EagerResult, so you should extract the record/node first.

Also, in save_entities() you accept:

entities: list[EntityNode]

but the Cypher says:

UNWIND $claims AS claim

and you pass:

entities=[...]

So the parameter naming is inconsistent. It would be cleaner to make this either claims throughout or actually implement entity creation there if that method is intended to save entities.

There is also an important architectural distinction I'd recommend: keep ingestion/write endpoints separate from exploration/read endpoints. Your current driver is primarily a persistence layer; the API layer should expose domain-oriented operations like /entities/{id}/graph, rather than mirroring methods such as save_claims() one-for-one.
